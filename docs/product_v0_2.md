## アーキテクチャ全体図

```
[CEO（Claude Code Max）]
  │
  │ ①バッチ生成（週 1 回／月 1 回）
  │   ・年齢帯×曜日テーマで 30 日分のお題テンプレを一括生成
  │   ・5 層ガードレール Layer 1-2 をプロンプトに埋め込み
  ▼
[配信ライブラリ（Google Sheets：無料）]
  ・1 行 = 1 配信（日付・年齢帯・テーマ・本文・声かけ台本・出典）
  ・ステータス列：draft / reviewed / published / retired
  │
  │ ②CEO 目視確認（Layer 4：強化版／配信前都度・全件）
  │   ・Sheets 上で 30 日分を 60 分でレビューし「reviewed」へ
  ▼
[公開チャネル：note（メイン）]
  ・毎日 1 本のお題記事を予約投稿
  ・無料記事 30%（集客）／メンバーシップ限定 70%（課金）
  │
  │ ③スケジュール配信
  │   ・note 予約投稿機能：完全無料・自動化
  │   ・補助：LINE Bot で「今週の note まとめ」週 1 プッシュ（200 通 / 月の無料枠内）
  ▼
[ユーザー（保護者）]
  ・note メンバーシップ ¥980/月で全記事閲覧
  ・LINE Bot で週次リマインド
  ・四半期オフ会で対面交流
  │
  │ ④フィードバック（Layer 3）
  ▼
[Google Forms（無料）]＋[note コメント]＋[オフ会会話]
  → CEO が次回バッチ生成のインプットに反映
```

**キーポイント**: LINE Bot は「毎日配信の主軸」から「週次リマインドの補助」に降格。note を「毎日体験」の主軸に昇格させる。LINE 無料枠 200 通／月 × 300 人 = 1.5 通／月以下に収まる。

## 1. コンテンツ生成・配信パイプライン

### 1-1. バッチ生成プロセス

**頻度**: **月 1 回（毎月最終週の土曜午前 3 時間）**

- 理由: 週次にすると CEO の月間生成コマが 4 回 → 心理的負荷大。月次なら「集中投下で 30 日分を一気に作る」運用が成立。
- 例外: 季節イベント（夏休み・運動会・入学準備）が直前にある月は、その 2 週間前に追加バッチを実施。

**1 バッチで生成する量**:

| セグメント | 1 日分 | 30 日分 | 月の総コマ数 |
|---|---|---|---|
| 0-2 歳（ペルソナ A） | 1 本 | 30 本 | 30 |
| 3-4 歳（年少・年中） | 1 本 | 30 本 | 30 |
| 5-6 歳＋低学年（年長・小 1-2） | 1 本 | 30 本 | 30 |
| **合計** | **3 本／日** | **90 本／月** | **90** |

**生成所要時間（Claude Code Max 範囲内）**:

- お題本文＋声かけ台本＋助け舟＋出典：1 本 5 分（Claude Code 対話形式で連続生成）
- 90 本 × 5 分 = 450 分（7.5 時間）→ **2 セッションに分割（土曜午前 3.5h ／午後 4h）**
- Claude Code Max の利用枠内に収まる前提（要実測検証）

### 1-2. CEO の目視確認プロセス（Layer 4 強化版）

- **タイミング**: バッチ生成直後（同じ日内）
- **対象**: 生成された 90 本すべて
- **所要時間**: 1 本あたり 60 秒 × 90 本 = 90 分（1.5 時間）
- **チェック観点（5 点）**:
  1. 危険・誤情報・誤嚥/アレルギーリスクのある食材推奨がないか
  2. 体罰・恫喝・ジェンダー固定観念表現がないか
  3. 医療判断（発達遅延の診断的言及）に踏み込んでいないか
  4. 公的資料の引用（出典 URL）が記載されているか
  5. 年齢帯に対して難度が適切か
- **判定**: Google Sheets の status 列で `reviewed` / `revised` / `rejected` の 3 値管理
- **`revised` は CEO 自身が手修正**（Claude Code に再生成依頼で 5 分）

### 1-3. 配信ライブラリの構造

**実装**: Google Sheets 1 シート（無料・無制限・公式 API あり）

| 列名 | 型 | 例 |
|---|---|---|
| id | string | 2026-06-01_3to4_mon |
| publish_date | date | 2026-06-01 |
| segment | enum | `0to2` / `3to4` / `5to6` |
| weekday_theme | enum | 文字／数／生活マナー／工作／読み聞かせ／自然／週次ふりかえり |
| title | string | ひらがな「し」を探そう |
| body_md | text | お題本文（Markdown） |
| script_for_parent | text | 親への声かけ台本 |
| help_fallback | text | 助け舟 |
| source_url | url | 文科省幼稚園教育要領 該当ページ |
| status | enum | draft / reviewed / revised / rejected / published / retired |
| review_note | text | CEO レビュー時のメモ |
| feedback_score | int | フィードバック「役立った」率 % |

**配信は Google Sheets → note 予約投稿への手動コピー**（Phase 1-2）。Phase 3 で Google Apps Script の自動投稿を検討（要 note 側仕様確認、保留事項）。

### 1-4. スケジュール配信実装

**メイン: note 予約投稿（完全無料・標準機能）**

- 月次バッチで生成した 90 本（30 日 × 3 セグメント）を、月初に note 上で 30 日分を予約投稿
- 予約投稿時刻: **平日 19:30 ／週末 9:30**（v0.1 のゴールデンタイム維持）
- メンバーシップ会員は当該セグメント記事を自動的に読める

**補助: LINE Bot 週次プッシュ（無料枠 200 通／月の範囲内）**

- 週 1 回（日曜夜）「今週の note 記事まとめ＋来週の予告」を配信
- 配信先: 全有料会員（300 人想定）→ 月 4 回 = **月 1,200 通**
- → **無料枠 200 通を超過するため、配信先を絞る or 頻度を下げる必要あり**
- 対応案 A: **月 1 回プッシュに変更**（300 通 / 月 → 依然 100 通超過）
- 対応案 B: **「初月のみリマインド受信、2 ヶ月目以降はオプトイン制」**（オプトイン率 30% = 90 人 × 月 4 回 = 360 通 → これも超過）
- 対応案 C（採用）: **LINE Bot は「無料枠 200 通の範囲で運用」と割り切り、月 1-2 回の重要告知のみに用途を絞る**。日常リマインドは note 通知（無料・標準機能・回数無制限）に任せる
- **結論**: LINE は「ライト接点」に格下げ。note メンバーシップ標準通知が日常リマインドの主役

**バックアップ: Gmail 手動配信（緊急時のみ）**

- 配信障害時の代替経路として、メールアドレスを任意項目で収集（プライバシーポリシー記載）
- 平時は使わない

## 2. パーソナライズ方針

### 2-1. 採用案：年齢帯セグメント別配信（3 セグメント）

- セグメント設計：
  - **A. 0-2 歳**（ペルソナ A：発達観察＋親の安心メッセージ）
  - **B. 3-4 歳**（年少・年中：生活習慣＋言葉の芽）
  - **C. 5-6 歳＋低学年**（年長・小 1-2：就学準備＋ひらがな数）
- ユーザーは登録時に自分の子の年齢を選択し、該当セグメントの note メンバーシップに加入

### 2-2. 不採用案と理由

| 案 | 不採用理由 |
|---|---|
| (1) 全員同じ毎日のお題（無セグメント） | 0-2 歳と 5-6 歳の困りごとが根本的に異なる（ペルソナ v0 で確認済）。1 本では誰にも刺さらない |
| (3) ユーザーが選ぶタグでフィルタリング | UI 複雑度増・選択疲れ。CEO 側の生成負荷もタグ組合せ分爆発 |
| (4) AI による個別生成（v0.1 案） | Claude API 不採用方針で実現不可 |

### 2-3. セグメントが 3 つで運用が成立する根拠

- 1 セグメント月 30 本 × 3 = 月 90 本。CEO のバッチ生成・レビュー工数で吸収可能（1-1, 1-2 で試算済）
- 3 セグメントは「親が "うちの子はここ" と一発で判断できる粒度」かつ「個人運営で破綻しない上限」のバランス点

### 2-4. パーソナライズ感の演出（同一コンテンツでも体験差を作る工夫）

- 子のニックネーム差し込み（note メンバーシップ登録時の任意入力 → 記事テンプレに `{{nickname}}` 差し込み）※note 標準機能では未対応のため Phase 2 で検証、当面は固定文
- 「あなたのセグメントの今週ベスト 3」を週末記事で配信し、選ばれた感を作る
- 月次「あなたの子はこの 30 日でこの 6 つに取り組みました」自動レポート（Google Sheets→ note 半自動）

## 3. 配信チャネル戦略

### 3-1. LINE 無料枠制約の正確な把握

- LINE 公式アカウント **コミュニケーションプラン**：月額 ¥0、**200 通／月まで、超過後の追加配信不可**
- ライトプラン（¥5,000／月 5,000 通）・スタンダードプラン（¥15,000／月 30,000 通）は **採用不可**（Claude Code 以外課金不可方針）
- 出典：[LINE公式アカウントの料金プラン｜LINEヤフー for Business](https://www.lycbiz.com/jp/service/line-official-account/plan/)、[Messaging APIの料金 | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/pricing/)

### 3-2. 300 人 × 毎日配信の数学的不可能性

- 300 人 × 30 日 = **9,000 通／月**（無料枠 200 通の **45 倍**）
- 仮に週 1 配信でも 300 人 × 4 回 = **1,200 通／月**（依然 **6 倍**）
- → **LINE を「日常配信チャネル」として使う設計はすべて破綻**

### 3-3. 採用するチャネルミックス

| チャネル | 役割 | 頻度 | コスト | 役割降格／昇格 |
|---|---|---|---|---|
| **note メンバーシップ（昇格・主役）** | 毎日のお題配信＋集客＋課金 | 毎日 1 本 / セグメント | 無料（手数料のみ） | v0.1 補助 → v0.2 主軸 |
| **note 無料記事（継承）** | SEO 集客・LP 代替 | 月 4-8 本 | 無料 | 同等 |
| **LINE Bot（降格）** | 重要告知のみ（月 1-2 回） | 月 1-2 回プッシュ | 無料（200 通/月内） | v0.1 主軸 → v0.2 補助 |
| **Gmail（バックアップ）** | 障害時／オフ会告知の代替 | 不定期 | 無料 | 新規 |
| **オフ会（継承）** | 解約防止・リアル交流 | 四半期 1 回 | 参加費で実費賄う | 同等 |

### 3-4. 課金が必要な選択肢（参考・採用しない）

> 以下は「制約を外せば成立するが、Claude Code 以外課金不可方針により採用しない」案。トレードオフの可視化目的で記載。

- **[採用しない・課金フラグ]** LINE ライトプラン（¥5,000／月、5,000 通／月）: 300 人 × 月 4 回プッシュ = 1,200 通で収まる
- **[採用しない・課金フラグ]** LINE スタンダードプラン（¥15,000／月、30,000 通／月）: 300 人 × 毎日配信 9,000 通が無料枠内に収まる
- **[採用しない・課金フラグ]** SendGrid / Mailchimp 有料プラン: Gmail での個別送信より大量配信に向く

### 3-5. note を主役にするメリット・デメリット

| 観点 | メリット | デメリット |
|---|---|---|
| 集客 | note プラットフォームの SEO 力・回遊・話題化を活用 | プラットフォーム規約変更リスク |
| 課金 | メンバーシップ標準機能で課金・解約・領収書を完結 | 売上の 10-20% が手数料（[note 公式](https://prtimes.jp/main/html/rd/p/000000360.000017890.html)） |
| 運用 | 予約投稿・コメント・通知が標準機能 | テンプレ差し込みなど高度な機能は不可 |
| 解約防止 | 過去記事アーカイブが資産化 | 解約 = 過去記事も読めなくなる仕様（強い解約防止フック） |
| ブランディング | サブドメイン `note.com/<username>` で完結、独自ドメイン不要 | URL がブランドのコアにならない（許容） |

## 4. 5 層ガードレール更新

### 4-1. 各層の v0.1 → v0.2 変更

| 層 | v0.1 | v0.2 | 変更点 |
|---|---|---|---|
| Layer 1: プロンプト設計 | システムプロンプト固定 | **Claude Code のプロジェクト memory（CLAUDE.md／.claude/agents/）に固定** | 仕組み化 |
| Layer 2: 公的資料引用 | 同左 | 同左＋出典 URL 必須化（配信ライブラリの `source_url` 列） | 出典の物理担保 |
| Layer 3: ユーザーフィードバック | LINE Bot「役立った／違和感」2 択 | **note コメント＋ Google Forms（無料）の "今週どうでした" 簡易アンケート** | LINE 頻度低下に対応 |
| Layer 4: CEO レビュー | 月 1 回・30-60 分・抜き取り | **配信前都度・全件・1 本 60 秒 × 90 本＝月 1.5 時間（強化）** | ユーザー確定事項 |
| Layer 5: コミュニティ検閲 | オフ会で吸い上げ | 同左（変更なし） | 同等 |

### 4-2. Layer 4 強化の意味

- 配信前 100% 目視 → **「販売コンテンツは CEO が目視確認する」確定事項の物理的実現**
- 工数増加：v0.1 月 1 時間 → v0.2 月 1.5 時間（許容範囲）
- AI 生成リスクの責任を CEO に明示的に置く構造になり、免責文言とも整合

## 5. note × オフ会との連携更新

### 5-1. note 記事カレンダー再設計（バッチ生成型に適合）

**月の記事構成（1 セグメントあたり）**:

| 種類 | 月の本数 | 課金 |
|---|---|---|
| 毎日のお題（メンバーシップ限定） | 30 本 | ¥980/月 メンバーシップ |
| 週末ふりかえり（無料） | 4 本 | 無料・集客用 |
| SEO 検索流入記事（無料） | 4-8 本 | 無料・LP 代替 |
| 月次成長レポート（メンバーシップ限定） | 1 本 | ¥980/月 |
| 季節特集（単発有料） | 月 1-2 本 | ¥500 |

**月の総本数**: 1 セグメント約 40 本 × 3 セグメント = **約 120 本／月**

- うち、バッチ生成（Claude Code）対象：毎日のお題 90 本 + 月次レポート 3 本 = 93 本
- CEO 自身が執筆：週末ふりかえり 12 本 + SEO 記事 4-8 本 + 季節特集 3-6 本 = 約 20-26 本

### 5-2. オフ会で集めた「リアルな保護者の声」をバッチ生成のインプットに活用

- オフ会終了直後（翌週月曜）に CEO が議事録化（既存 `mtg-management:mtg-manager` スキル活用）
- 「保護者の困りごと TOP5」「使えなかった既存サービスの不満」を抽出
- 次月バッチ生成時の Claude Code 指示プロンプトに「今月のリアル声」として注入
- 効果：AI 生成お題が「現場の悩みベース」になり、表面的なテンプレ感を回避

## 6. 収益モデル再計算

### 6-1. コスト再計算（v0.1 → v0.2）

| 項目 | v0.1 | v0.2 | 差分 |
|---|---|---|---|
| Claude API | ¥7,000-12,000 | **¥0**（Claude Code Max に内包） | -¥7,000-12,000 |
| LINE Messaging API | ¥0-5,000 | **¥0**（無料枠内運用） | -¥0-5,000 |
| Stripe 決済手数料 | ¥9,000 | **¥0**（note メンバーシップに統合、note 側手数料は売上から控除） | -¥9,000（別計上） |
| note 手数料（売上の約 10-20%） | - | **約 ¥30,000-60,000**（¥30 万売上時） | 新規 |
| サーバ | ¥0-3,000 | **¥0**（note ホスティング・Google Sheets で代替） | -¥0-3,000 |
| 監修者 | ¥0（v0.1 で削減済） | ¥0 | 同等 |
| ドメイン | ¥2,000 | **¥0**（独自ドメイン不採用） | -¥2,000 |
| Claude Code Max | - | **¥約 3,000（個人サブスク・既存固定費）** | 既存固定 |

## 7. ユーザー価値の維持戦略

### 7-1. 「バッチ生成でも毎日新しい体験」を作る 5 つの工夫

1. **note 予約投稿で「今日届いた感」を演出**：閲覧時刻に応じて「今日のお題」表示
2. **曜日テーマで体験リズムを作る**（v0.1 踏襲）：月＝文字、火＝数、水＝生活マナー…
3. **季節要素を月次バッチに必ず注入**：5 月＝こどもの日、6 月＝雨、7 月＝水遊び…
4. **読者投稿の翌月反映**：オフ会・コメントの声を翌月バッチに織り込み、「自分の声が反映された」体験
5. **月次成長レポートの個別化**：閲覧履歴ベースで「あなたが今月読んだ 20 本」を可視化

### 7-2. 「個別 AI 生成ではない」ことをむしろ強みにする

- **訴求文**：「AI のテンプレ生成ではなく、CEO（編集長）が全件読んで磨き上げた毎日のお題」
- AI 生成リスクの開示（v0.1 既出）と整合し、「CEO の手が入っている安心感」をブランド資産化
